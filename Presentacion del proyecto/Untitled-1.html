3.1 Actividad de Reflexión Inicial (0.5 Horas)

Sistemas como Black Friday, inscripciones universitarias o plataformas de boletas suelen colapsar. Analicemos el porqué antes de escribir la primera línea de código de prueba.

Bug Funcional vs Saturación

Un bug es una falla de lógica en el código (ej. cálculo incorrecto). Un fallo por saturación ocurre cuando los recursos de hardware (CPU, RAM, DB Connections) se agotan por concurrencia masiva.

Impacto Organizacional

Una caída del sistema implica pérdida de ventas directas, daño irreparable de la reputación de la marca y posibles penalizaciones contractuales o legales.

Insuficiencia Unitaria

Las pruebas unitarias y de integración prueban la app con 1 solo usuario. No simulan contención de hilos, bloqueos en base de datos ni saturación de sockets de red.

Tarea de Autoevaluación

Redacta una breve conclusión respondiendo: ¿Por qué una API que responde perfectamente en Postman con 1 petición puede fallar con 500 solicitudes al tiempo?

3.2 Contextualización: Tipos de Pruebas de Rendimiento

Rendimiento (Performance)

Carga Normal

Mide la velocidad y latencia bajo condiciones normales de operación.

Métrica: Response Time (ms)
Carga (Load Testing)

Carga Esperada

Evalúa el comportamiento con la cantidad esperada de usuarios activos.

Métrica: Concurrency / CPU-RAM
Estrés (Stress Testing)

Punto de Quiebre

Lleva al sistema más allá del límite para hallar el *Breaking Point* y tiempo de recuperación.

Métrica: Error Rate (%)
Picos (Spike Testing)

Súbitas Ráfagas

Aumentos drásticos e instantáneos de tráfico para probar la resiliencia.

Métrica: Recovery Time
Volumen (Volume)

Base de Datos

Prueba el rendimiento con millones de registros almacenados en la base de datos.

Métrica: DB Query Time
JMeter vs K6

GUI Java vs Scripting JS optimizado en Go para CI/CD
